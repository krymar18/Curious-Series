Context & Craft

Context is the fuel. Prompting technique is how efficiently you burn it. This page skips the basics and covers what separates a working prototype from something reliable enough to ship.

Objective

Cover what separates a working prototype from something reliable enough to demo or ship — not the basics.

Key idea

Context engineering asks a different question than prompt engineering: not "what should I say," but "what should be sitting in the model's attention right now — and what shouldn't."

Context Engineering

Once you're running multi-turn work instead of one-off asks, what's in the context matters more than how you phrased the ask.

Why More Context Isn't Better

Every token added costs attention. Transformers relate every token to every other token — an n² problem, not a linear one. Past a point, more context means a thinner attention budget spread across more competing signals.

Anthropic's research calls this context rot: recall degrades as the window fills, even before you hit the hard limit. Not a cliff — a slope, and it starts earlier than people expect.

The rule: the smallest set of high-signal tokens that gets the outcome beats the biggest set of relevant ones. Minimal doesn't mean short — it means nothing in there that isn't earning its place.

Same principle, one level up: a system prompt that's too specific is brittle if-else logic that breaks on the first case you didn't anticipate. Too vague, and the model fills the gap with a guess. Aim for specific enough to steer, loose enough to survive a case you didn't write down.

Building, Moving, and Storing Context

Before you start: sort what already exists, what needs cleaning, and what needs creating from scratch.

Moving between chats: a long thread isn't memory — it's a liability that happens to contain memory. Ask for a state summary (decisions, facts, open questions) or a full handoff prompt: goal, assumptions, sources, format, and what not to re-litigate.

Storing outside the chat: a project brief, decision log, glossary, and prompt library survive the thread ending and let a human audit fact versus assumption. Proof of concept — a shared doc is enough. Production — the same idea becomes a retrieval index or governed knowledge source.

Surviving Tasks Longer Than One Context Window

Three distinct techniques, not interchangeable — each fixes a different failure mode.

TechniqueWhat it doesBest for
CompactionSummarize the conversation near its limit, restart with the summary plus what was last actually touchedLong back-and-forth that needs to keep flowing
Structured note-takingThe AI keeps a running notes file outside the context window and reads it back after a resetMulti-step work with clear milestones
Sub-agent delegationA focused sub-task runs in its own clean context, then returns a short summary instead of its full working historyResearch or exploration that shouldn't cost context everywhere else

None of these are "start a new chat and hope." That's the failure mode all three exist to prevent.

Tips to Try

Four prompts worth keeping on hand.

Build a project brief

"Ask me the minimum set of questions needed to understand this project, then turn my answers into a one-page project brief with goal, users, constraints, source material, assumptions, and open questions."

Write a handoff prompt

"Write a prompt I can paste into a new chat so the next assistant understands this project, the current state, the preferred style, and what not to revisit."

Separate fact from assumption

"Review the context below and divide it into confirmed facts, assumptions, risks, and items that need validation before use."

Test context quality

"Using only the context provided, answer these three test questions. If the answer is missing or uncertain, say what context is needed instead of guessing."

Advanced Prompting Techniques

Six techniques that hold up under real production pressure, not just a demo.

Structured Output

Ask for JSON or XML against a defined schema so a downstream step parses it instead of scraping prose. Three things need to be explicit: the task, the schema (field names, types, allowed values), and a hard constraint that only that structure comes back — no preamble, no markdown fencing.

Sample flow — AI Builder in Power Automate:

  1. Trigger: "When a new email arrives," filtered to the emails you want.
  2. Run a Prompt action, JSON output on, schema like {"customer_name":"","priority":"","issue_category":""}.
  3. Branch or route directly on the returned fields — no string-splitting.
  4. Send an email or create a record using the fields as dynamic content.

If AI Builder won't generate valid JSON, add: "don't include JSON markdown in your answer."

Grounding on Long Documents

Ask the model to quote the relevant passage before answering — it cuts through the noise of a long document. Two placement rules move the needle measurably: long documents near the top of the prompt, the actual question at the bottom. In Anthropic's own testing, query-after-document plus quote-first improved multi-document answer quality by up to 30%.

Sequences and Reasoning Budget

Transformers process tokens in parallel — no native counter, no built-in sense of "step 4 of 7." That's why long numbered procedures drift, and "give me the 12th item" is a coin flip.

Fix: force sequencing into the output. Explicit step markers in structured output, chain-of-thought or extended thinking to work through order before answering, and a self-check — "recount the steps, confirm no gaps or repeats" — for anything that matters.

Reasoning budget: API and Claude Code builders are moving from manually-set thinking budgets to adaptive thinking — an effort level (low/medium/high/max), not a token guess. Copilot Chat manages this internally; there's no user-facing dial.

Calibrating Prompts and Tools

System prompt altitude: too specific and it's brittle if-else logic that breaks on the first unanticipated case. Too vague and the model guesses. Rewriting a prompt every time a new edge case appears is a sign it's pitched too low.

Tool sets: a bloated toolset with overlapping jobs doesn't add capability — it adds ambiguity. If a person on the team can't say which tool should fire for a request, the model can't either. Fewer, sharper tools beat a big toolbox.

XML tags to separate instructions from data

Wrap data as <document>, <source>, <document_content>, and keep instructions outside those tags. Without a clear boundary, a model can quote instructions back as data, or treat data as an instruction to follow.

Conclusion & Reflections

Take a moment to reflect — it's what makes the learning stick.

Key Takeaways
  • Context rot is real — more tokens isn't more knowledge, it's a thinner attention budget.
  • Compaction, structured note-taking, and sub-agent delegation fix different failure modes. Pick the one that matches the task, not the one you know.
  • Structured output turns AI from something you read into something a system can run on.
  • AI has no native counter — sequences need to be forced into the output, not assumed.
  • Fewer, sharper tools and a well-pitched system prompt beat more of either.
Reflection
  • Where have you seen a long chat quietly get worse before it hit any hard limit?
  • Pick a long-running task you own. Which of the three survival techniques actually fits it?
  • Is there a workflow where you're reading AI output and re-typing it into a system by hand? That's a structured-output candidate.
  • What's one tool or instruction you've added to a prompt "just in case" that's never actually fired?
