Technical Translation

Objective

Use AI to bridge natural language and formal language — generating code, reformatting data, and explaining technical output — without needing to be a technical expert.

Core idea

AI reads your plain-language description and produces formal output by pattern-matching against the enormous volume of code and technical writing in its training data. It does not run the code to check if it works. The rule for this entire category: test on a known sample before using at scale.

Translation Without Validation

The core mechanic — and the core limitation — of everything in this category.

AI reads your plain-language description and produces formal output — code, formulas, specifications — by pattern-matching against the enormous volume of code and technical writing in its training data. It does not run the code to check if it works. A formula that is syntactically correct but logically wrong looks identical in the output. The rule for this entire category: test on a known sample before using at scale.

Writing Code

Generating working code from a plain-language description — Excel formulas, Office Scripts, Python, SQL queries, Power Automate logic, technical specifications, and mockups. Describe what you want; AI produces the syntax. You do not need to understand the code to use this in low-stakes contexts. You do need to test it before it touches real data or live systems.

Copilot in Power Automate and Excel use exactly this mechanism.

↗ Where this is most useful
  • Writing Excel formulas for lookups, calculations, and conditional logic
  • Generating SQL queries to pull specific data from a database
  • Drafting Power Automate flows to automate a described sequence of steps
  • Writing Office Scripts to process or format a worksheet automatically
  • Producing a Python script to read, transform, or analyse a data file
  • Writing a technical user story or requirements document for a new feature
  • Describing a UI or workflow and receiving a structured spec back

What AI handles vs. what you must own

AI
  • Writing syntactically correct code from plain-language descriptions
  • Producing technical specifications and mockup descriptions from intent
  • Generating multiple approaches with trade-offs described
Human
  • Testing the output on a known sample before using it on real data
  • Verifying the logic is correct, not just the syntax
  • Providing business rules and edge cases AI cannot infer
  • Deciding which approach to implement when AI gives options

Limitations and how to address them

A formula or script that runs without errors can still produce wrong results. Syntactic correctness is not logical correctness.
How to address it
Test on a small sample with known expected outputs before running on real data. If the sample output matches what you expected, scale up.
AI does not know your specific system constraints, data quirks, or business rules unless you provide them. The code it generates handles the general case, not your environment.
How to address it
Describe edge cases explicitly: "what should happen if the value is blank?" or "what if there are duplicate rows?" Code that does not handle edge cases will fail in production.
AI-generated code can be difficult to modify later if you do not understand it. If you need to maintain or adapt it, you may not know where to start.
How to address it
At the time of generation, ask AI to explain the code step by step and add comments. This is much easier to do now than after the fact.

Additional lifehacks

  • Ask AI to explain what the code does before you use it — if the explanation does not match your intent, the code is wrong.
  • For Power Automate flows: describe trigger, conditions, and actions in that order — it produces cleaner output.
Tradeoff
Quick working draft vs. robust, production-ready code

A clear description gets you a working draft quickly — accept that edge cases will need manual addition afterwards, and treat the output as a starting point to modify rather than a finished product to deploy. For production-ready code, describe edge cases in the prompt, ask for the code in steps with explanations, and test on a known sample before scaling. It is slower, but far easier to debug and maintain.

Reformatting Data and Documents

Using AI to transform data or documents from one structure to another — without the user needing to write or understand any code. Describe the target format, paste the source, and AI returns it restructured. The code is invisible; the user only sees input and output. This is the same capability as Writing Code, but framed for users who would never engage with "write me a Python script" but will readily engage with "clean up this data for me".

↗ Where this is most useful
  • Standardising inconsistently formatted data from a system export
  • Extracting specific fields from a set of similar documents into a unified table
  • Cleaning a dataset — removing duplicates, standardising date formats, flagging blanks
  • Converting unstructured notes into a numbered SOP or structured report
  • Restructuring a spreadsheet with merged cells or inconsistent headers
  • Adding calculated fields to a dataset
  • Reformatting free-text CRM notes into consistent structured records

What AI handles vs. what you must own

AI
  • Restructuring data from one format or layout to another
  • Cleaning inconsistencies, duplicates, and blanks
  • Extracting consistent fields from multiple documents into a unified output
Human
  • Verifying the restructured output before using it downstream
  • Defining the target structure clearly — AI produces what you describe, not what you meant
  • Checking that no data was silently dropped, duplicated, or modified

Limitations and how to address them

Do not paste sensitive data — client records, financial data, personal information — into a general AI tool. Check your organisation's data handling policy first.
How to address it
For sensitive data: share only column headers and a description of what you need, then ask AI to write the transformation code. Run the code locally in your own environment. The data never leaves.
AI may silently drop, modify, or incorrectly transform edge-case rows. A bad transformation looks correct until something downstream breaks.
How to address it
Show AI one example output row first. Confirm it is right. Then ask it to apply the same format to the full dataset. For large datasets, test on a 10-row sample before scaling.
AI produces what you describe, not what you meant. An imprecise description of the target format produces an output that is internally consistent but wrong for your purpose.
How to address it
Always ask AI to flag rows it cannot transform rather than guess: "if any row cannot be formatted due to missing or ambiguous data, flag it". Silence on a problem row is worse than a flag.

Additional lifehacks

  • For field extraction across multiple documents: number the documents before pasting, then ask AI to include the source document number in each output row so you can trace back.
Tradeoff
Fast transformation vs. accurate and repeatable

Pasting directly and describing the target format works for smaller, cleaner inputs — accept that unusual edge cases may need manual correction after. For accuracy and repeatability — especially on recurring transformations — show one example output row first, confirm it is correct, then apply to the full set. For large datasets, generate the transformation code and run it locally: you can rerun it as data changes, and the data stays private.

Explaining and Documenting Code

Asking AI to explain what existing code, a formula, or automation logic does — or to document it so others can understand, maintain, or modify it. This is the reverse of Writing Code: formal input in, plain-language explanation out. Debugging sits here too — explaining why something is not working is explanation applied to a failure rather than a function.

↗ Where this is most useful
  • Understanding what an inherited formula, script, or flow does before modifying it
  • Diagnosing why a formula or script is producing an error or unexpected output
  • Generating plain-language documentation of an automation for a non-technical approver
  • Writing a runbook for a process so others can maintain it
  • Adding comments to existing code before handing it over
  • Explaining a technical integration to a non-technical stakeholder

What AI handles vs. what you must own

AI
  • Explaining in plain English what code, formulas, or flows do
  • Identifying the likely cause of an error and suggesting a fix
  • Generating documentation, comments, and runbooks from existing code
Human
  • Testing any suggested fix on a known sample before applying it to production
  • Providing the error message, context, and what the code is supposed to do — AI cannot debug without these
  • Making the final call on whether to apply a fix or rewrite from scratch

Limitations and how to address them

AI explanations describe what the code appears to do. They may miss subtle bugs or unintended behaviours that only appear with specific inputs.
How to address it
After reading the explanation, run the code on a sample with known expected outputs. If the output does not match the explanation, the explanation or the code — or both — is wrong.
For debugging: AI identifies likely causes based on pattern recognition. It is not running the code. Environment-specific issues may not be visible to it.
How to address it
Always paste the error message alongside the code. "It is not working" is not useful. The error message is the starting point.
If AI's explanation does not match what you expected the code to do, that discrepancy is the bug — not just a misunderstanding.
How to address it
Use the discrepancy as the starting point for the fix. Ask: "The explanation says X but I expected Y — what in the code causes this difference?"

Additional lifehacks

  • Ask AI to explain AND identify potential issues in one prompt — even working code often has edge cases worth knowing about.
  • For documentation: ask AI to write for a specific reader — "for someone who will maintain this but did not write it" produces more useful output than a generic documentation request.
Tradeoff
Fast orientation vs. reliable, accurate explanation

Asking for a plain-English summary gets you oriented quickly — useful before a deeper read — but a high-level explanation may miss conditional logic or edge cases. For a reliable explanation, ask for step-by-step breakdown: slower, but it exposes the logic that a summary compresses. In both cases, verify by running the code and checking that the output matches what AI described.

Functionality Spotlight

A live exercise using a sample Excel dataset. Download it, run the prompts in Copilot inside Excel, and see why explaining a formula before using it is not optional.

Exercise goal

Ask Copilot to write a formula, then ask it to explain that formula step by step before running it on anything real. If the explanation does not match your intent, the formula is wrong — even if it runs without an error. Then test it on the sample data where the correct answer is already known.

Questions to ask yourself
  • Did the explanation match what you actually needed the formula to do?
  • What happened on the rows with blank cells — did the formula handle them or break?
  • Would you have caught that error if you had skipped the explanation step?
  • What is the difference between a formula that runs and a formula that is correct?
Sample prompts to try

Open the dataset in Excel, format it as a Table, then open the Copilot panel. Run the prompts in order — do not skip to Prompt 3 without completing Prompt 2 first.

1 Write the formula
Copy prompt

Write an Excel formula that calculates the variance between Budget and Actuals as a percentage. If Actuals is blank, return "Missing" instead of an error.

Do not use the formula yet. Read it first.

2 Explain it first
Copy prompt

Explain this formula step by step in plain English. What does each part do? What happens when Actuals is blank? What happens if Budget is zero?

If the explanation does not match your intent, the formula is wrong.

3 Test on a known sample
Copy prompt

Apply this formula to the first three rows of the dataset. Show me the result for each row and confirm what the expected output should be based on the numbers.

Check the output against rows where you already know the answer.

Two things to keep in mind after you run this

  • A formula that runs without errors is not the same as a formula that is correct. Syntactic correctness and logical correctness are different things — the explanation step is what bridges them.
  • Edge cases are where formulas fail in production. Blank cells, zero values, and unexpected text in a numeric column are not rare — they are guaranteed. Ask Copilot how the formula handles them before you scale it.
