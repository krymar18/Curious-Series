Explain Code or a Formula You Did Not Write

Paste an inherited formula, script, or automation step and ask Copilot to explain what it does and flag potential issues — before you use or modify it.

8 – 10 min Copilot Chat M365 Copilot Premium
1
Find something to explain
You
▶
Do this
Find a formula, script, or automation step you use or maintain but do not fully understand. Paste it into Copilot Chat.
2
Ask for a step-by-step explanation
Copilot Chat
▶
Do this
Paste the code and send this prompt:
Prompt 1 — Explain

Explain what this [formula / script / flow] does in plain English. Walk through it step by step. After the explanation, tell me: what are the edge cases where it might behave unexpectedly or produce wrong results?

◉
Look for
Does the explanation match what you thought it was doing? If there is a discrepancy between what you expected and what Copilot describes, that discrepancy is the thing to investigate — not a misunderstanding.
3
Test the explanation
Excel or your environment
▶
Do this
Run the code on a small sample with 3–5 rows where you know the expected output. Does the output match what Copilot described?
4
Document it while you understand it
Copilot Chat
▶
Do this
In the same thread, ask Copilot to write documentation while the understanding is fresh:
Prompt 2 — Document it

Write a plain-language comment for each section of this code that a non-technical person who will maintain it later could follow. Written for someone who did not write it and needs to know what to change and what not to touch.

◈
Reflect
Documentation written at the time of understanding is far more useful than documentation written later. If you have just understood a piece of code for the first time, this is the right moment to document it.
Key Takeaways
  • If Copilot's explanation does not match what you expected the code to do, that discrepancy is the bug — use it as the starting point for the fix.
  • AI explanations describe what the code appears to do. They may miss subtle bugs that only appear with specific inputs. Always verify on a known sample.
  • The best time to document inherited code is the moment you understand it for the first time. After that moment, the documentation gets harder and less accurate.
